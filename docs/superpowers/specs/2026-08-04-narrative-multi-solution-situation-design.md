# GRIMOIRE Narrative Multi-Solution Situation Design

## 1. 문서 상태

```yaml
project: "GRIMOIRE: 세계를 다시 쓰는 법"
decision_id: GM-NARRATIVE-MULTI-SOLUTION-SITUATION-01
status: USER_APPROVED_DESIGN_WRITTEN_READY_FOR_SPEC_REVIEW
approved_at: 2026-08-04T00:27+09:00
work_mode: GPT_CREATIVE_PLANNING
implementation: NOT_STARTED
codex: DEFERRED
```

이 문서는 GRIMOIRE의 사건 콘텐츠를 **텍스트 노벨식 상황 선택과 주문 설계가 결합된 복수 해결 구조**로 정의한다.

핵심 원칙은 다음과 같다.

> 텍스트 선택지는 해결 의도와 우선순위를 정한다. 실제 실행법과 성공 여부는 이후 주문 설계, 상황 조건, 결과 대가가 결정한다.

---

## 2. 채택 방향

### 2.1 핵심 플레이 루프

```text
사건 제시
→ 조사·대화·관찰
→ 해결 의도와 우선순위 선택
→ 선택한 접근에 맞는 주문 설계
→ 직접 작성·Stock·소환수 중 실행 수단 선택
→ 세계 상태 변화
→ 추가 변수와 후속 선택
→ 결과·대가·발견 기록
```

### 2.2 두 단계 선택

#### 1차 선택 — 해결 접근

플레이어는 무엇을 우선할지 결정한다.

예:

- 시설 복구
- 생명 구조
- 원인 조사와 교섭
- 현상 봉쇄
- 전투·강제 제압

#### 2차 선택 — 주문 실행

같은 접근 안에서도 여러 주문이 가능하다.

예:

```text
생명 구조 선택
→ 보호 통로
→ 지정 이동
→ 냉기 흐름 우회
→ 임시 온도 유지
```

텍스트 선택지가 주문 조합을 자동 선택해서는 안 된다.

---

## 3. 핵심 재미 정의

> 상황을 읽고 자신이 중요하다고 판단한 해결 방향을 선택한 뒤, 의미를 가진 글자로 그 의도를 실제 주문으로 구현하고 결과와 대가를 책임지는 재미.

### 3.1 필수 감정

- `내가 문제를 해석했다.`
- `내가 무엇을 지킬지 정했다.`
- `내가 그 의도를 주문으로 구현했다.`
- `결과가 왜 발생했는지 이해했다.`
- `다른 방식으로 다시 해결해 보고 싶다.`

### 3.2 금지되는 퇴행

- 정답 선택지 찾기
- 호감도 정답 맞히기
- 공격 주문만 효율적인 전투 RPG
- 선택 직후 자동 성공
- 주문 설계가 선택지 연출에 종속
- 도덕적으로 좋은 선택과 나쁜 선택의 단순 구분

## 4. Situation Challenge 구조

모든 대표 사건은 다음 데이터를 가진다.

```yaml
situation:
  immediate_goal: 현재 반드시 처리해야 할 문제
  observable_states: 플레이어가 직접 확인 가능한 정보
  hidden_causes: 조사·대화·감지로 발견할 정보
  stakeholders: 영향을 받는 인물·생명·시설·정령
  pressures: 시간·마나·위험·관계·자원
  approach_choices: 해결 의도와 우선순위
  spell_constraints: 접근별 주문 설계 조건
  valid_endings: 복수의 유효한 해결 상태
  costs: 각 해결에서 남는 피해·소모·관계 변화
  discoveries: 마도서에 남는 활용과 실패 원인
```

### 4.1 관찰 정보 규칙

- 기본 화면에는 핵심 상태 3~5개만 표시한다.
- 추가 정보는 조사·대화·소환수 관찰·감지 주문으로 얻는다.
- 필수 정답 정보를 특정 관계 선택 하나에 독점시키지 않는다.
- 정보 부족 상태에서도 안전한 해결 접근이 최소 하나는 존재한다.

### 4.2 접근 선택 규칙

- 선택지는 **행동 목적**을 표현한다.
- 선택지는 주문 이름이나 조합을 직접 제시하지 않는다.
- 각 접근은 장점과 포기 비용을 가진다.
- 모든 사건에서 전투 접근을 강제하지 않는다.
- 접근은 후속 정보에 따라 수정할 수 있다.
- 초반 선택이 결말을 완전히 잠그지 않는다.

## 5. 복수 정답 계약

### 5.1 유효 해결의 정의

유효 해결은 다음 조건을 만족한다.

1. 선택한 우선순위와 주문 결과의 인과가 설명 가능하다.
2. 사건의 핵심 위협이 제거·완화·봉쇄·이관된다.
3. 발생한 대가가 명시적으로 기록된다.
4. 최소 하나의 후속 반응 또는 마도서 발견을 만든다.
5. 다른 해결과 비교 가능한 차이를 가진다.

### 5.2 결말 상태 예시

```yaml
valid_endings:
  - COMPLETE_RESTORATION
  - LIFE_FIRST_EVACUATION
  - SPIRIT_RECONCILIATION
  - SAFE_CONTAINMENT
  - FORCEFUL_SUPPRESSION
  - PARTIAL_RECOVERY_WITH_COST
```

하나의 `TRUE_ENDING`을 두지 않는다. 다만 사건별로 위험 관리 실패, 인명 피해, 통제 상실 등 명확한 실패 상태는 존재할 수 있다.

### 5.3 최소 해법 수

대표 사건은 다음을 충족해야 한다.

```yaml
minimum_approaches: 3
minimum_noncombat_approaches: 2
minimum_valid_spell_plans_per_approach: 2
minimum_valid_endings: 3
```

Vertical Slice 대표 사건은 권장치로 접근 5개를 사용한다.

## 6. 대표 사건 — 서리꽃 온실의 심장

### 6.1 사건 개요

마법학교 서리꽃 온실의 중심 마력로가 멈췄다. 희귀 묘목이 얼어가고, 마력 배관이 균열되며, 냉기를 흡수한 정령들이 불안정해졌다. 관리 학생 한 명은 내부에 고립돼 있다.

정령이 원인처럼 보이지만 조사하면 이들 역시 냉기 누출의 피해자일 수 있다.

### 6.2 기본 관찰 정보

- 중심 핵 정지
- 배관 결빙과 압력 상승
- 서리꽃 묘목 상태 악화
- 불안정한 서리 정령
- 고립 학생 위치

### 6.3 숨은 정보

- 정령은 핵을 파괴하지 않았다.
- 배관 내부 균열이 냉기 폭주의 원인이다.
- 핵 강제 재가동은 배관 파열을 유발할 수 있다.
- 정령 안정화 시 누출 위치를 감지하는 데 도움을 줄 수 있다.

---

## 7. 대표 접근 5개

### A. 시설 복구

의도:

> 온실 핵과 배관을 되살려 전체 상황을 정상화한다.

주문 후보:

- `열 + 집중` — 배관 정밀 해빙
- `열 + 분산` — 온실 전체 온도 회복
- `흐름 + 유도` — 마력 공급 우회
- `보호 + 고정` — 균열 임시 봉합

대가:

- 구조와 정령 안정화가 늦어질 수 있음
- 과열 또는 마력 역류 위험

### B. 생명 구조 우선

의도:

> 학생과 묘목을 먼저 구하고 시설 피해를 감수한다.

주문 후보:

- `보호 + 선형` — 안전 통로
- `이동 + 지정` — 고립 학생 이동
- `보호 + 확장` — 묘목 구역 격리
- `열 + 지속` — 임시 생존 온도 유지

대가:

- 시설 손상 증가
- 후속 복구 비용 발생

### C. 정령 안정화·교섭

의도:

> 정령의 폭주 원인을 이해하고 비전투 방식으로 협력한다.

주문 후보:

- `보호 + 안정` — 마력 변동 완화
- `감지 + 연결` — 정령 감각 공유
- `흐름 + 분산` — 냉기 부담 분산
- `보호 + 원형` — 안전한 교섭 구역

대가:

- 시간이 오래 걸림
- 묘목이나 시설 일부 손상 가능

### D. 현상 봉쇄

의도:

> 완전 해결보다 확산 방지와 대피를 우선한다.

주문 후보:

- `보호 + 고정` — 출입구 봉인
- `흐름 + 역전` — 냉기 외부 확산 차단
- `열 + 지속` — 임시 온도 유지
- `감지 + 확대` — 위험 경계 추적

대가:

- 사건이 후속 임무로 남음
- 온실 일부를 포기할 수 있음

### E. 전투·강제 제압

의도:

> 정령을 처치하는 것이 아니라 복구 시간을 확보한다.

하위 방식:

- 공격으로 밀어냄
- 보호로 접근 차단
- 수호 소환수로 방어
- 유도 주문으로 특정 구역에 모음
- 냉기 공급을 끊어 무력화

대가:

- 정령 관계 악화
- 원인 이해 부족
- 빠른 복구 가능

전투는 다섯 접근 중 하나이며 기본값이 아니다.

## 8. 직접 작성·Stock·소환수 관계

### 8.1 직접 작성

- 새로운 해결법과 중요한 판단을 표현한다.
- 자유도가 높지만 시간이 필요하다.
- 사건의 핵심 주문 하나 이상은 직접 작성한다.

### 8.2 Stock

- 이미 이해한 글자를 빠르게 삽입한다.
- 사건 접근을 자동 선택하지 않는다.
- 사용 시점과 이후 비축 손실이 판단 요소다.

### 8.3 소환수

- 관찰, 수호, 견제, 구조 보조로 시간과 정보를 제공한다.
- 주문의 글자 선택·연결·Commit을 대신하지 않는다.
- 전투 외에도 조사·안정화·운반 지원에 활용한다.

## 9. 텍스트 노벨 UX

### 9.1 장면 흐름

```text
상황 서술
→ 핵심 인물 반응
→ 조사 가능한 요소 표시
→ 접근 선택
→ 접근별 조건 요약
→ 주문 설계 화면
→ 결과 연출
→ 추가 변수 또는 후속 선택
```

### 9.2 선택지 문장 규칙

좋은 선택지:

- `온실 핵을 복구한다.`
- `학생과 묘목을 먼저 구조한다.`
- `정령이 폭주한 원인을 조사한다.`
- `현장을 봉쇄하고 지원을 요청한다.`
- `정령을 제압해 시간을 확보한다.`

금지 선택지:

- `열 + 집중을 쓴다.`
- `정답을 고른다.`
- `착하게 정령을 돕는다.`
- `나쁘지만 빠르게 공격한다.`

### 9.3 선택 정보량

- 한 화면의 핵심 접근 선택지는 3~5개다.
- 세부 조사 선택은 2~4개다.
- 각 선택지에는 결과 정답이 아니라 예상 경향만 표시한다.

예:

```text
시설 복구
- 전체 문제를 정상화할 가능성
- 초기 구조가 늦어질 위험
```

## 10. 결과 평가와 마도서

단일 총점 대신 다축 기록을 사용한다.

```yaml
evaluation_axes:
  - situation_understanding
  - life_protection
  - facility_preservation
  - mana_efficiency
  - risk_management
  - creative_spell_use
  - spirit_relationship
  - decision_responsibility
```

### 10.1 결과 인과 표시

```text
선택한 접근
→ 사용한 글자와 보조
→ 세계 상태 변화
→ 성공한 부분
→ 남은 피해와 대가
→ 새로 발견한 활용
```

### 10.2 실패 구분

```text
INPUT_FAILURE
GRAMMAR_FAILURE
SITUATION_DESIGN_FAILURE
PRIORITY_FAILURE
RESOURCE_EXHAUSTION
```

입력 실패를 기획 판단 실패로 기록하지 않는다.

### 10.3 마도서 기록

마도서에는 완성 주문 이름만 남기지 않는다.

- 사건 조건
- 선택한 우선순위
- 사용한 글자
- 작동 원인
- 대가
- 다음 연구 목표

을 함께 기록한다.

## 11. 반복 플레이와 분기 비용

### 11.1 재플레이 가치

- 다른 접근 선택
- 같은 접근에서 다른 주문 설계
- 새로운 조사 정보 발견
- 다른 우선순위와 결과 비교
- 마도서 활용 기록 완성

### 11.2 제작비 통제

분기마다 독립 맵과 장면을 만들지 않는다.

```text
공통 사건 장면
+ 상태 변화 레이어
+ 인물 반응 변형
+ 접근별 주문 조건
+ 결과 태그
```

으로 재사용한다.

대사 분기는 핵심 반응과 결과 설명 중심으로 제한하고, 장문 독립 루트는 Vertical Slice에서 만들지 않는다.

## 12. 적대적 검토와 보완

### 위험 1 — 텍스트 선택이 이미 정답을 결정

보완:

- 선택은 의도만 고정한다.
- 주문 설계에 최소 두 가지 실행법을 남긴다.
- 후속 변수로 접근 수정이 가능하다.

### 위험 2 — 모든 접근이 결국 같은 결과

보완:

- 보호 대상, 시설 상태, 관계, 자원, 발견 기록을 다르게 남긴다.
- 단순 대사 차이가 아니라 세계 상태 태그를 변경한다.

### 위험 3 — 비전투 접근이 느리고 손해

보완:

- 교섭·봉쇄·구조에도 독점적 장점과 발견을 제공한다.
- 전투 접근은 속도와 안전 시간을 주되 관계·원인 이해 비용을 가진다.

### 위험 4 — 분기량 폭증

보완:

- 접근은 3~5개로 제한한다.
- 접근별 주문 후보를 데이터 계약으로 재사용한다.
- 결과는 조합 가능한 상태 태그로 생성한다.

### 위험 5 — 플레이어가 무엇을 해야 할지 모름

보완:

- 접근 선택 전 핵심 상태 3~5개를 명확히 보여준다.
- 결과 경향은 보여주되 정답과 구체 주문은 숨긴다.
- 메인 동반자는 조건을 해석하지만 결정을 대신하지 않는다.

### 위험 6 — 선악 선택으로 퇴행

보완:

- 모든 접근에 보호 대상과 포기 비용을 둔다.
- 인물마다 평가 관점이 다르다.
- 총점으로 도덕적 우열을 확정하지 않는다.

```yaml
valid_endings_minimum: 3
independent_large_branch_maps: 0
```

첫 Slice에서는 모든 주문 후보를 실제 콘텐츠로 구현할 필요는 없다. 각 접근에서 최소 두 개의 유효 주문 계획을 제공해 구조를 검증한다.

## 14. 승인 기준

플레이테스트 후 다음이 확인돼야 한다.

1. 플레이어가 접근 선택과 주문 선택의 차이를 설명한다.
2. 전투가 유일한 해결법이라고 인식하지 않는다.
3. 최소 두 개의 서로 다른 접근이 유효하다고 느낀다.
4. 선택 후에도 자신이 주문을 설계했다고 느낀다.
5. 결과와 대가의 인과를 설명한다.
6. 다른 해결법으로 재시도하고 싶어 한다.
7. 텍스트 노벨 구간과 주문 플레이가 하나의 사건으로 연결됐다고 느낀다.

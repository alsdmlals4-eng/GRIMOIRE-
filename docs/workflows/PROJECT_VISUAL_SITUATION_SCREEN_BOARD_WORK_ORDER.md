# 프로젝트 비주얼 중심 「상황별 인게임 화면 명세 보드」 작업지시문

## 문서 상태

```yaml
workflow_id: PROJECT-VISUAL-SITUATION-BOARD-01
decision_id: GM-VISUAL-SITUATION-BOARD-WORKFLOW-01
status: ACTIVE_PROJECT_WORK_ORDER
approval: APPROVED_PROJECT_WORK_PRINCIPLE
scope: CROSS_PROJECT_TEMPLATE_WITH_PROJECT_SPECIFIC_APPLICATION
base_promotion: CANDIDATE
implementation_authority: NONE
supersedes_primary_output_role_of: PROJECT-SITUATION-SCREEN-SPEC-01
previous_technical_spec_role: SUPPORTING_APPENDIX_ONLY
```

이 작업지시문의 목적은 기술 감사 보고서를 만드는 것이 아니라, **“이 프로젝트가 구현되면 실제로 어떻게 보이는가”**를 비주얼·필수 화면·핵심 화면 시퀀스 중심으로 정리하는 것이다.

기술 구조·데이터·테스트·위험 분석은 필요하더라도 메인 화면 보드 뒤의 구현 명세 부록으로 분리한다.

---

# 0. 작업 핵심 의도

최우선 질문:

1. 프로젝트가 구현되면 어떤 비주얼 톤으로 보이는가.
2. 플레이어가 가장 자주 보는 필수 화면은 어떻게 구성되는가.
3. 핵심 플레이 상황에서 화면은 어떻게 변하는가.
4. UI·UX·와이어프레임 방향은 무엇인가.

메인 산출물은 다음이다.

```text
프로젝트 비주얼 기준 보드
→ 필수 기준 화면 4종 보드
→ 핵심 상황별 화면 시퀀스 보드
→ 전체 화면 전환도
→ 구현 명세 부록
```

금지되는 중심:

- 프로젝트 감사 보고서.
- 구현 위험 보고서.
- Scene·Signal·Controller 표 중심 대시보드.
- 작은 글씨로 모든 정보를 한 장에 넣은 종합 보고서.

---

# 1. 작업 전 확인 순서

1. 사용자의 최신 요청.
2. 프로젝트 `AGENTS.md`.
3. `docs/BASE_RULES_VERSION.md`.
4. `docs/DOCUMENTATION_MAP.md`.
5. 프로젝트 내부 Base 로컬 사본·Adapter·Snapshot.
6. 프로젝트 README·전용 규칙.
7. 현재 Goal·Issue·Planning 문서.
8. 실제 Scene·Script·Resource·데이터 파일.
9. 기존 와이어프레임·UI 시안·이미지 자료.

Base 원격은 일상 작업의 기본 입력으로 반복 조사하지 않는다. 프로젝트에 동기화된 로컬 사본과 버전 문서를 우선 사용한다.

문서와 실제 파일이 다르면 다음을 분리한다.

- 문서에서 확인된 방향.
- 실제 구현 파일에서 확인된 화면.
- 구현되지 않은 기획.
- 재구성을 위해 필요한 해석.
- 사용자 결정이 필요한 신규 제안.

확인하지 않은 요소를 현재 구현 또는 확정안처럼 표현하지 않는다.

---

# 2. 산출물의 핵심 기준

최종 결과는 다음 질문에 직접 답해야 한다.

1. 비주얼 톤은 무엇인가.
2. 메인 화면은 어떻게 보이는가.
3. 전투 또는 핵심 플레이 화면은 어떻게 보이는가.
4. 인벤토리 또는 자원 관리 화면은 어떻게 보이는가.
5. 결과 화면은 어떻게 보이는가.
6. 핵심 상황에서 화면은 어떻게 변하는가.
7. 플레이어는 무엇을 보고, 누르고, 이해하는가.

상대적으로 뒤로 미룬다.

- 상세 Controller 분해.
- 과도한 Scene·Signal 표.
- 과도한 위험·감사 표.
- 기술 감리형 대시보드.

---

# 3. 근거 수준 표기

모든 화면·요소·시각 예시는 다음 태그 중 하나를 표시한다.

| 태그 | 의미 |
|---|---|
| `CURRENT` | 실제 프로젝트 문서·파일·기존 시안에서 확인 |
| `INFERRED` | 확인된 자료를 바탕으로 합리적으로 재구성 |
| `PROPOSED` | 현재 프로젝트에 필요한 신규 제안 |
| `PLACEHOLDER` | 임시 예시용 시각 자료 |

규칙:

- `CURRENT`와 `PROPOSED`를 한 화면에서 섞을 경우 요소별 라벨이나 명확한 영역 분리를 사용한다.
- 프로젝트에 없는 그림체·로고·캐릭터·UI를 현재 확정안처럼 만들지 않는다.
- 생성 이미지에는 보드 전체 또는 각 화면에 근거 태그를 표시한다.
- 기존 시안을 재구성할 때는 원본 프로젝트의 인물·마스코트·화면 구조를 우선 보존한다.

---

# PART A. 프로젝트 비주얼 기준 보드

## 목적

프로젝트가 어떤 시각 언어를 가져야 하는지 한눈에 파악하게 한다.

## 포함 항목

### A-1. 핵심 경험 요약

- 장르.
- 플랫폼.
- 플레이어 역할.
- 핵심 판타지.
- 핵심 감정.
- 대표 세일즈포인트.
- 상징 요소·마스코트.
- 유사 장르와 구별되는 차별점.

### A-2. 현재 비주얼 방향

- 그림체.
- 캐릭터 표현 방식.
- 배경 표현 방식.
- UI 스타일.
- 컬러 팔레트.
- 폰트 계층.
- 아이콘 스타일.
- 버튼·패널 스타일.
- 강조 효과.
- 금지 시각 요소.

### A-3. 상태 구분

- 확정 사항.
- 확인 필요 사항.
- 신규 제안 사항.

## 출력 규칙

- 설명은 짧고 명확하게 작성한다.
- 시각 예시·색·실루엣·구도·UI 샘플이 텍스트보다 먼저 보이게 한다.
- 기술 구조는 이 파트에 넣지 않는다.

---

# PART B. 필수 기준 화면 4종 보드

## 필수 화면

1. `SCREEN-01` 메인 화면.
2. `SCREEN-02` 전투 또는 핵심 플레이 화면.
3. `SCREEN-03` 인벤토리 또는 자원 관리 대응 화면.
4. `SCREEN-04` 결과 화면.

전통적 전투나 인벤토리가 없는 프로젝트는 문서와 실제 파일에서 대응 화면을 찾는다. 대응 화면이 없으면 `NOT_APPLICABLE` 또는 `PROPOSED`로 표시한다.

## 화면별 최소 표기

- SCREEN ID.
- 화면명.
- 화면 목적.
- 핵심 플레이어 행동.
- 가장 중요한 정보 3개.
- 이전 화면.
- 다음 화면.
- 근거 수준.
- 현재 구현 상태.

## 화면 표현 규칙

- 화면은 UI가 판독 가능한 크기로 배치한다.
- 한 장에 너무 많은 화면을 축소해 넣지 않는다.
- 각 화면은 독립 보드 또는 충분한 크기의 2×2 보드로 구성한다.
- 기술 표보다 실제 화면 구도·HUD·버튼·캐릭터·배경을 우선한다.

## 상태 변형

### SCREEN-01 메인 화면

- 최초 실행.
- 저장 데이터 없음.
- 이어하기 가능.
- 공지·이벤트·업데이트 알림.
- 설정·서브 메뉴 복귀.

### SCREEN-02 전투·핵심 플레이

- 진입.
- 일반 조작.
- 위험 예고.
- 행동 선택.
- 조건 부족.
- 성공·우세.
- 피격·실패.
- 종료 직전.

### SCREEN-03 인벤토리·자원 관리

- 빈 상태.
- 일반 상태.
- 신규 획득.
- 비교.
- 장착·사용.
- 조건 미충족.
- 보유 한도 초과.

### SCREEN-04 결과

- 완전 성공.
- 부분 성공.
- 실패.
- 신규 해금.
- 재도전.
- 복귀.

프로젝트에 맞지 않는 상태는 제외할 수 있으나 제외 이유를 한 줄로 기록한다.

---

# PART C. 핵심 상황별 화면 시퀀스 보드

## 목적

Vertical Slice의 핵심 플레이 상황에서 화면이 어떻게 달라지는지 보여준다.

## 선택 범위

- 대표 상황 3~5개.
- 각 상황 4~8단계.
- 상황 설명보다 화면 변화 중심.

## 단계별 필수 표시

- 새로 보이는 정보.
- 사라지거나 비활성화되는 요소.
- 플레이어 행동.
- 강조 영역.
- 캐릭터·카메라·UI 변화.
- 성공·실패·전환 피드백.
- 이전·다음 단계 연결.

## 권장 시퀀스 표현

```text
[필드·상황 인지]
→ [대화·정보 획득]
→ [핵심 판단·작성·행동 선택]
→ [전투·상황 반응]
→ [결과·세계 변화]
→ [복귀·기록]
```

각 단계는 작은 기술 카드가 아니라 실제 인게임 화면 프레임으로 표현한다.

---

# PART D. 구현 명세 부록

시각 보드와 연결되는 최소 구현 정보만 기록한다.

- SCREEN ID·SIT ID별 Scene.
- 주요 Node 역할.
- Resource 데이터.
- Signal 개요.
- 상태 머신 개요.
- 화면 전환 방식.
- 저장·복귀 방식.
- 예외 처리.
- 테스트 체크리스트.
- 구현 우선순위.
- Codex Goal 후보.

규칙:

- PART D는 항상 메인 보드 뒤에 둔다.
- 기술 정보는 SCREEN ID·SIT ID를 참조한다.
- 메인 비주얼 보드보다 더 큰 지면을 차지하지 않는다.
- 자세한 기술 감사는 별도 문서로 연결한다.

---

# 4. 시각화 제작 규칙

1. 한 장에 과도한 텍스트를 넣지 않는다.
2. 화면은 판독 가능한 크기로 배치한다.
3. 작은 글씨의 기술 보고서처럼 만들지 않는다.
4. 표보다 화면 예시와 흐름을 우선한다.
5. 서로 다른 프로젝트도 같은 템플릿을 사용한다.
6. 현재안과 개선안은 명확히 구분한다.
7. 장르와 맞지 않는 일반 판타지 UI로 대체하지 않는다.
8. 프로젝트 고유의 핵심 감정·마스코트·선택·자원을 화면에 반영한다.
9. 플레이어 관점인 “직접 플레이하면 어떻게 보이는가”를 유지한다.
10. 이미지 생성 전 기존 이미지·시안·아트 방향을 먼저 읽는다.
11. 기존 이미지가 있으면 캐릭터 실루엣·비율·의상·마스코트 형태·화면 구도를 임의로 교체하지 않는다.
12. 신규 시각 요소는 `PROPOSED` 또는 `PLACEHOLDER`로 표시한다.

## 권장 보드 분할

한 장에 모든 내용을 넣지 않는다.

- Board 1: 프로젝트 비주얼 기준.
- Board 2: 필수 화면 `SCREEN-01 / SCREEN-02`.
- Board 3: 필수 화면 `SCREEN-03 / SCREEN-04`.
- Board 4~6: 핵심 상황 시퀀스 3개.
- Board 7: 전체 화면 전환도.
- Appendix: 기술 구조·테스트·결정.

필요하면 화면 하나를 한 장 전체로 사용한다.

---

# 5. 금지 사항

1. 기술 감사 보고서를 메인 산출물로 만드는 것.
2. 필수 화면을 축소해 UI가 읽히지 않게 만드는 것.
3. `CURRENT`와 `PROPOSED`를 섞어 확정안처럼 보이게 하는 것.
4. 프로젝트에 없는 아트 스타일을 현재 방향처럼 단정하는 것.
5. 필수 화면 4종을 텍스트 목록으로만 제시하는 것.
6. 핵심 상황을 글로만 설명하고 화면 변화는 보여주지 않는 것.
7. 한 장에 모든 것을 넣은 과밀 대시보드.
8. 프로젝트 고유 경험 대신 일반 게임 UI를 사용하는 것.
9. 이전 프로젝트 또는 다른 장르의 비주얼을 재사용하는 것.
10. 기존 주인공·마스코트·대표 화면을 근거 없이 새 캐릭터로 대체하는 것.

---

# 6. 적대적 검토 루프

초안 생성 후 다음 여섯 검토를 순서대로 수행한다. 실패 항목은 수정한 뒤 다시 판정한다.

## 1차 — 화면 중심성

질문:

- 기술 보고서보다 화면 보드로 보이는가.
- 첫 시선이 실제 화면으로 향하는가.

실패 조건:

- 표·판정·기술 구조가 화면보다 큼.

수정:

- 표 축소, 텍스트 감축, 화면 확대, 보드 분할.

## 2차 — 사용자 질문 충족

질문:

- 구현됐을 때의 실제 모습을 바로 이해할 수 있는가.
- 필수 화면 4종과 핵심 화면 변화가 보이는가.

실패 조건:

- 화면 4종이 부차적.
- 시스템 설명이 중심.

수정:

- 화면 4종을 앞쪽으로 이동, 시퀀스 확대, 부록 후행.

## 3차 — 근거 수준 분리

질문:

- `CURRENT / INFERRED / PROPOSED / PLACEHOLDER`가 구분되는가.

실패 조건:

- 신규 화면·스타일이 현재 확정안처럼 보임.

수정:

- 화면별 태그, 현재안·제안안 분리, 미정 유지.

## 4차 — 프로젝트 고유성

질문:

- 다른 프로젝트가 아니라 이 프로젝트답게 보이는가.
- 핵심 감정·세일즈포인트·마스코트가 드러나는가.

실패 조건:

- 일반 장르 Mockup.
- 기존 주인공·마스코트·고유 시스템이 사라짐.

수정:

- 프로젝트 이미지와 정본 재조회, 고유 요소 복구, 공용 템플릿 표현 완화.

## 5차 — 판독성·UX 가독성

질문:

- UI와 버튼을 읽을 수 있는가.
- 첫 3초 정보가 명확한가.

실패 조건:

- 화면이 작음.
- 정보 우선순위 불명확.
- 글씨 과밀.

수정:

- 화면 확대, 보드 분할, 정보 3계층 재정렬, 내용 축약.

## 6차 — 비교·재사용 가능성

질문:

# 9. 완료 기준

- 사용자가 구현 후 화면을 한눈에 이해할 수 있다.
- 메인·전투/핵심 플레이·인벤토리/자원 관리·결과 화면이 명확하다.
- 핵심 상황의 화면 변화가 시각적으로 드러난다.
- 비주얼과 UI·UX 방향이 정리돼 있다.
- 근거 수준이 구분된다.
- 기술 구조가 메인 보드를 압도하지 않는다.
- 프로젝트 간 비교 가능한 템플릿을 유지한다.
- 적대적 검토를 통과했다.

# 10. Base 승격 후보와 프로젝트 전용 항목

## Base 승격 후보

- 비주얼 중심 상황 화면 명세 템플릿.
- 필수 화면 4종 기준.
- `CURRENT / INFERRED / PROPOSED / PLACEHOLDER` 규칙.
- 6단계 적대적 검토 체크리스트.
- 공통 화면 전환도 표기 규칙.
- 화면 판독성·보드 분할 규칙.

## 프로젝트 전용 유지

- 프로젝트 고유 그림체.
- 세계관·마스코트·감정 톤.
- 고유 자원·전투·조사·제작 구조.
- 프로젝트 전용 화면 연출.
- 특정 게임의 상태 변형.
- 실제 기존 이미지에서 확인된 캐릭터·의상·비율·배경·상징.

# 11. 이전 작업지시문과의 관계

`PROJECT-SITUATION-SCREEN-SPEC-01`의 A~T 기술 구현 명세는 폐기하지 않는다. 다만 다음 역할로 제한한다.

```text
새 비주얼 중심 화면 보드
= 사용자 검토의 1차 산출물

기존 A~T 상황별 구현 명세
= PART D 기술 부록·Codex Plan 입력 자료
```

기존 기술 명세나 기술 중심 이미지가 새 비주얼 보드보다 앞에 나오거나, 현재 프로젝트의 대표 화면처럼 사용되어서는 안 된다.

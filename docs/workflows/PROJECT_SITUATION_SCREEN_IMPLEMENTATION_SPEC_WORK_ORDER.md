# 프로젝트 상황별 인게임 화면 설계 및 구현 명세 작업지시문

## 문서 상태

```yaml
workflow_id: PROJECT-SITUATION-SCREEN-SPEC-01
status: ACTIVE_PROJECT_WORK_ORDER
scope: PROJECT_SPECIFIC_APPLICATION
base_promotion: CANDIDATE
implementation_authority: NONE
```

이 작업지시문은 각 프로젝트에서 플레이어가 실제로 경험하는 상황을 도출하고, 예상 인게임 화면·시스템·데이터·Godot 구조·전환·검증을 코드 작성 전에 설계하기 위한 공통 형식이다.

---

# 1. 작업 목표

프로젝트의 기획 문서, 시스템 문서, 데이터 구조, 실제 파일을 분석한 뒤 플레이어가 진행 중 마주칠 대표 상황을 도출한다.

각 상황에서 다음을 설계한다.

- 발생 맥락과 진입 조건.
- 플레이어가 보고 느껴야 하는 것.
- 실제 인게임 화면 구성과 정보 우선순위.
- 선택·조작·취소·복구 방식.
- 작동하는 시스템과 데이터.
- Godot 4.x Scene, Node, Resource, Signal, 상태 머신 구조.
- 화면 전환과 상태 유지.
- 완료 기준과 테스트 방법.

이 작업은 메뉴 목록이나 UI 목록을 만드는 작업이 아니다.

```text
상황
→ 플레이어 판단
→ 입력
→ 조건·비용 검증
→ 시스템 반응
→ 결과
→ 데이터 변화
→ 다음 상황
```

전체 흐름을 구현 가능한 명세로 만든다. 현재 단계에서는 GDScript, Scene, Resource, 게임 데이터, 자산을 직접 구현하지 않는다.

---

# 2. 프로젝트 확인 순서

1. 사용자의 최신 지시.
2. 프로젝트 루트 `AGENTS.md`.
3. `docs/BASE_RULES_VERSION.md`.
4. `docs/DOCUMENTATION_MAP.md`.
5. 프로젝트에 동기화된 Base 로컬 사본·Adapter·Snapshot.
6. 프로젝트 README·전용 규칙·Active Context·현재 확정 결정.
7. 현재 Goal, Issue, 작업 계획, Draft PR.
8. 실제 `project.godot`, Scene, Script, Resource, 데이터, 테스트, 자산 파일.

Base 원격 저장소를 일상 작업마다 반복해 전수 조사하지 않는다. 프로젝트 내부의 버전 핀·동기화 사본·Adapter를 우선 사용하고, 누락·충돌·신규 Base 기능 확인이 필요한 경우에만 원격을 제한적으로 확인한다.

## 2.1 사실 분류

분석 결과는 반드시 다음으로 구분한다.

- `CONFIRMED_DOCUMENT`: 프로젝트 정본에서 확정.
- `IMPLEMENTED_FILE`: 실제 제품 파일에서 확인.
- `PLANNED_NOT_IMPLEMENTED`: 기획은 있으나 구현 없음.
- `INTERPRETATION`: 확정 내용을 연결해 도출.
- `PROPOSAL`: 신규 제안.
- `ASSUMPTION`: 명세 완성을 위한 임시 가정.
- `USER_DECISION_REQUIRED`: 사용자 승인이 필요한 내용.
- `PLAYTEST_TUNING_REQUIRED`: 런타임·사람 검증 후 수치 결정.

파일을 실제로 확인하지 않은 상태에서는 “이미 구현되어 있다”, “연결되어 있다”고 단정하지 않는다.

---

# 3. 벤치마킹 선행

새 시스템, 핵심 규칙, 콘텐츠 구조, UX 흐름을 설계하거나 의미 있게 변경할 경우 프로젝트 벤치마킹 정책에 따라 `QUICK / STANDARD / DEEP` 중 적절한 규모를 먼저 수행한다.

- 최근 동일한 결정 질문의 유효한 벤치마킹은 재사용 가능.
- 공식·1차 자료 우선.
- `ADOPT / ADAPT / REJECT` 기록.
- 레퍼런스의 고유 UI·아트·서사를 복제하지 않고 설계 원리만 적용.

# 4. 프로젝트 핵심 정의

화면 설계 전에 다음을 작성한다.

## 프로젝트 핵심 정의

- 장르.
- 1차 플랫폼과 후속 플랫폼.
- 예상 플레이 세션.
- 플레이어 역할.
- 핵심 판타지.
- 핵심 감정.
- 주요 선택.
- 주요 고민.
- 주요 보상.
- 기억에 남아야 할 장면.
- 대표 세일즈포인트.
- 마스코트·상징 요소.
- 유사 장르와 구별되는 차별점.

## 핵심 플레이 루프

```text
게임 시작
→ 첫 행동
→ 정보 또는 자원 획득
→ 상황 판단
→ 선택 또는 조작
→ 위험·비용 발생
→ 결과 확인
→ 성장·상태 변화
→ 다음 목표
```

## 화면 설계 원칙

각 화면은 다음 역할 중 하나 이상을 가져야 한다.

- 현재 상황을 이해시킨다.
- 중요한 선택을 제시한다.
- 위험과 보상을 비교시킨다.
- 결과의 원인을 보여준다.
- 캐릭터·세계에 감정을 느끼게 한다.
- 다음 행동 동기를 만든다.

역할이 없는 화면은 만들지 않는다.

# 5. 현재 시각·UI·UX 상태 조사

다음을 확정·제안으로 분리해 정리한다.

- 그림체와 캐릭터 표현.
- 배경 표현.
- UI 디자인 언어.
- 컬러 팔레트.
- 폰트 계층.
- 아이콘·테두리·패널·버튼 스타일.
- 애니메이션·전환 스타일.
- 프로젝트 상징 요소.
- 입력 방식.
- 반복 피로와 접근성.
- 실제 구현 파일과 현재 상태.

아트 스타일, 내부 해상도, UI 최종 치수처럼 미승인 항목은 명세에서 확정하지 않는다.

# 6. 필수 기준 화면 4종

대표 상황을 자유롭게 도출하기 전에 다음 네 기준 화면을 먼저 조사한다.

1. `SCREEN-01` 메인·시작 화면.
2. `SCREEN-02` 전투 또는 프로젝트의 핵심 플레이 화면.
3. `SCREEN-03` 인벤토리 또는 보유 지식·자원 관리 대응 화면.
4. `SCREEN-04` 결과 화면.

전통적 전투나 인벤토리가 없는 프로젝트는 대응 화면을 찾는다.

- 대응 화면이 있으면 원래 명칭과 역할을 함께 기록.
- 없으면 `NOT_DEFINED` 또는 `NOT_APPLICABLE`.
- 신규 화면 필요 시 `PROPOSAL`로 분리.

## 각 기준 화면 필수 항목

### 6.1 현재 정의 상태

- 문서 설명.
- 실제 Scene·UI 파일.
- 연결 Script.
- 연결 Resource·데이터.
- 구현 여부.
- 임시 UI 여부.
- 문서·파일 불일치.
- 미확인 항목.

### 6.2 시각 방향

- 그림체, 캐릭터, 배경, UI, 컬러, 폰트, 아이콘, 패널, 버튼, 전환, 상징 요소.

### 6.3 UX 방향

- 화면 방문 목적.
- 가장 자주 수행하는 행동.
- 최초 정보.
- 주요 행동까지 입력 수.
- 오작동 방지.
- 취소·복귀.
- 초보 안내.
- 숙련 단축 조작.
- 반복 피로.
- 접근성.

### 6.4 현재 확인안·개선 제안안 와이어프레임

문서·실제 구현에서 확인되는 배치와 신규 제안을 분리한다.

### 6.5 구성요소 표

| 구성요소 | 역할 | 위치 | 표시 조건 | 입력 | 현재 상태 |
|---|---|---|---|---|---|

### 6.6 상태별 변형

최소 검토 상태:

- 최초 진입.
- 일반.
- 선택 중.
- 빈 상태.
- 잠김.
- 신규 정보.
- 최대치·가득 참.
- 오류·조건 부족.
- 전환 중.
- 튜토리얼 중.

### 6.7 화면 연결

- 진입 경로.
- 이탈 경로.
- 뒤로 가기.
- 유지 데이터.
- 저장 시점.
- 로딩 구간.
- 중복 입력 방지.

### 6.8 Godot 구현 명세

- Scene·Node 구조.
- 재사용 UI Scene.
- 화면 전용 Scene.
- Resource.
- Signal.
- 상태 머신.
- 입력.
- 해상도.
- 저장.
- 오디오.

### 6.9 완료 기준

- 시각·UX 방향 일치.
- 주요 행동 명확.
- 정상·빈·잠김·오류 상태 정의.
- 다른 핵심 화면과 전환 명확.
- 기존 파일과 신규 필요 요소 구분.
- 지원 플랫폼에서 입력·배치 성립.

# 7. 대표 플레이 상황 도출

상황은 메뉴 이름이 아니라 **특정 플레이 맥락과 목적이 있는 순간**으로 정의한다.

상황 유형:

- 첫인상·진입.
- 탐색.
- 대화.
- 선택.
- 준비.
- 핵심 플레이·전투.
- 제작·조립.
- 성장.
- 위험.
- 실패.
- 승리.
- 보상.
- 복귀.
- 반복 플레이.
- 장기 진행.

각 상황은 의미가 포함된 ID와 이름을 함께 사용한다.

```text
SIT-001-첫-현장-진입
SIT-002-이상-징후-관찰
SIT-003-해결법-선택
```

숫자 ID만 단독 사용하지 않는다.

# 8. 상황 우선순위

| 상황 | 발생 빈도 | 핵심 재미 | 감정 중요도 | 구현 위험 | 차별성 | 우선순위 |
|---|---:|---:|---:|---:|---:|---|

- `P0`: Vertical Slice 필수 핵심 상황.
- `P1`: 핵심 경험 완성에 필요한 기능.
- `P2`: 다양성·편의성.
- `P3`: 폴리싱·확장.

P0를 상세 작성한다. P1~P3는 요약 명세를 먼저 만들고 필요할 때 확장한다.

# 9. 상황별 인게임 화면 구현 명세 형식

각 P0 상황은 다음 A~T 형식을 동일하게 사용한다.

## [상황 ID] 상황명

### A. 상황 개요

- 발생 이유.
- 현재 목표.
- 알고 있는 정보.
- 모르는 정보.
- 위험.
- 보상.
- 감정.
- 핵심 선택.
- 다음 상황.

### B. 근거와 가정

- 확정.
- 실제 구현.
- 해석.
- 제안.
- 가정.
- 사용자 결정 필요.

### C. 진입 조건

- 이전 상태.
- 트리거.
- 진행 플래그.
- 플레이어·월드 상태.
- 진입 불가 조건.
- 중복 진입 방지.

### D. 화면 목적

1. 최초 인지 정보.
2. 다음 확인 정보.
3. 행동 전 비교 정보.
4. 행동 후 결과 정보.

### E. 예상 인게임 화면

텍스트 와이어프레임과 다음을 포함한다.

- 화면비.
- 카메라.
- 플레이 공간.
- HUD·정보·입력·팝업·경고·결과 영역.
- 강조 요소.
- 최초 3초 정보.

### F. 화면 구성요소

| 요소 | 역할 | 표시 조건 | 숨김 조건 | 입력 | 우선순위 |
|---|---|---|---|---|---|

배경, 플레이어, 동료, NPC, 적, 대상, 목표, 자원, 행동, 선택지, 대사, 튜토리얼, 경고, 상태 이상, 보상, 결과, Pause·Back을 검토한다.

### G. 플레이어 입력

| 입력 | 조건 | 시스템 반응 | 피드백 | 실패·제한 |
|---|---|---|---|---|

현재 플랫폼에 존재하는 이동·선택·확인·취소·드래그·길게 누르기·대상 지정·단축 입력만 포함한다. 후속 플랫폼 입력은 별도 후보로 구분한다.

### H. 상황 진행 흐름

단계마다 다음을 표기한다.

- 자동·수동.
- 취소 가능.
- 저장 가능.
- 실패 가능.
- 반복 가능.

### I. 시스템 반응

| 플레이어 행동 | 조건 | 즉시 반응 | 데이터 변화 | 장기 영향 | 다음 상태 |
|---|---|---|---|---|---|

조건 부족, 비용 부족, 오대상, 중복 입력, 취소, 시간 초과, 실패, 부분 성공, 완전 성공을 포함한다.

### J. 필요한 시스템

| 시스템 | 역할 | 입력 데이터 | 출력 데이터 | 연결 시스템 |
|---|---|---|---|---|

### K. Godot 구현 구조

Node Tree와 각 Node의 책임, 소유 데이터, Signal, Scene 분리, 재사용성, 기존 구조 연결 가능성을 설명한다.

### L. Scene 분리 기준

다음 중 추천안을 선택한다.

1. 별도 Scene 전환.
2. 기존 Scene 내부 상태.
3. CanvasLayer Overlay.
4. 재사용 UI Scene.
5. SubViewport.

SubViewport는 별도 렌더가 실제로 필요한 경우에만 사용한다.

### M. Signal 및 상태 전환

```text
ENTER
→ INTRO
→ PLAYER_CONTROL
→ ACTION_SELECTION
→ RESOLVING
→ RESULT
→ EXIT
```

상태별 진입 조건, 허용 입력, 종료 조건, 유지 데이터, 취소 여부를 기록한다.

### N. 데이터 구조

| 데이터 | 주요 필드 | 저장 위치 | 변경 주체 | 저장 필요 |
|---|---|---|---|---|

Situation, Character, Action, Condition, Cost, Reward, Result, Flag, World, Save, View Data를 검토한다.

관리 방식은 기존 구조 우선이며, 신규 제안 시 Godot Resource·JSON·CSV·Google Sheets의 역할을 구분한다.

### O. 화면 전환 시 유지 데이터

- 위치.
- 캐릭터 상태.
- 자원.
- 선택·결과.
- 진행 플래그.
- 적·대상 상태.
- Camera.
- BGM 위치·상태.
- 일회성 연출.
- 복귀 Scene·Marker.

`반드시 유지 / 상황 종료 초기화 / Save 기록 / 세션 전용`으로 분류한다.

### P. 연출 명세

전환, Camera, Animation, UI 순서, 강조, 공격·피격, 성공·실패, BGM, SFX, 진동, 흔들림을 설명한다. 판정과 핵심 정보를 가리는 연출은 제외한다.

### Q. 필요한 애셋

| 애셋 | 용도 | 상태·변형 | 우선순위 | 임시 대체 가능 |


# 14. 보호 규칙

- 프로젝트에 없는 기능을 확정 사실로 만들지 않는다.
- 레퍼런스 이미지를 복제하지 않고 프로젝트 코어에 맞게 변환한다.
- Unity, C#, MonoBehaviour, Prefab 용어를 사용하지 않는다.
- Godot 4.x, GDScript, Scene, Node, Resource, Signal 용어를 사용한다.
- UI와 도메인 판정을 분리한다.
- 애니메이션 완료를 게임 판정 권위로 사용하지 않는다.
- 화면 전환 중 입력을 잠근다.
- Node 참조를 Save 데이터로 저장하지 않는다.
- 미승인 아트·수치·입력을 확정하지 않는다.
- 구현하지 않은 테스트를 통과했다고 주장하지 않는다.
- 사용자 승인 전 Codex·구현 단계로 넘어가지 않는다.

# 15. 프로젝트 적용 결과 분류

각 Scene·시스템·데이터는 다음으로 분류한다.

- 기존 구조로 그대로 가능.
- 기존 구조 확장 필요.
- 신규 시스템 필요.
- 현재 해당 없음.
- 사용자 결정 필요.
- 플레이테스트 조정 필요.

# 16. Base 승격 기준

다음은 프로젝트 공통성이 입증되면 Base 승격 후보가 될 수 있다.

- 상황→판단→입력→반응→결과→다음 상황 템플릿.
- 필수 기준 화면 4종 감사.
- 확정·구현·해석·가정 분류.
- P0~P3 우선순위.
- World Scene·Overlay·Snapshot 전환 계약.
- 상황별 완료 기준·테스트 체크리스트.

프로젝트 고유 글자, 전투 규칙, 서사, 인물, 자원, UI 언어는 프로젝트 전용으로 유지한다.
